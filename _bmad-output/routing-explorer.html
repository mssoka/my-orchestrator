The model at a glance

One deterministic tick: spawn → route → serve → deliver or drop

Every tick, flow_step (core/flow.odin) does this. Routing is a one-shot BFS at spawn; the route is then cached on the packet and held until something demolishes a pipe under it. Bandwidth is shared per-pipe and scheduled by QoS lane — that's a different axis from routing, and the artifact keeps them separate on purpose.

① Current behavior · core/flow.odin · compute_route

BFS, walked one step at a time

Routes are shortest by hop count — not by tier, not by cost. The graph is the adjacency list; neighbors come out in pipe-insertion order, and the first pipe to discover a node "claims" it. Pick a source and sink, then step through the expansion. The shaded trail is bfs_prev walked back into the final pipe path.

🍍 BFS in 30 seconds — the three moving parts

Breadth-First Search explores the graph one ring at a time — all 1-hop neighbors first, then all 2-hop, then 3-hop… so the first time it reaches the sink, that route is provably shortest by hop count. Three pieces run it:

① the queue

A FIFO list of nodes to expand next. Seeded with [src]. Each step pops the front node and looks at its neighbors.

→ the exploration order. “Breadth-first” = finish a whole ring before starting the next.

② visited

A set of already-discovered nodes. Skip any neighbor already in it — so each node is enqueued exactly once.

→ prevents loops + redundant work. (The obvious one — you called it.)

③ bfs_prev ★ the key one

A map node → the node we discovered it from. The breadcrumb trail. The loop only records who-claimed-whom — it does not build the path.

→ after the loop you walk back: dst → prev[dst] → prev[…] → src, then reverse. That reversed list is the path.

So why two passes? BFS deliberately separates discovery (scatter breadcrumbs across the graph) from reconstruction (follow them home). It keeps the hot loop branch-free and deterministic — which is why compute_route is a BFS loop followed by a walk-back, and why no RNG is needed: insertion order alone decides every tie. Watch the bfs_prev column fill as you step; the green trail is exactly that map walked back, each hop then resolved to a concrete pipe by pick_pipe.

The actual Odin (cited verbatim) 
// compute_route — BFS over adjacency (insertion-ordered) -> per-hop parallel-pipe pick.
for head < tail {
    cur := f.bfs_queue[head]; head += 1
    if cur == dst_slot { found = true; break }
    n := neighbors(t, t.node_id[cur], nb_buf[:])
    for i in 0 ..< n {
        ns, ok := node_slot(t, nb_buf[i])
        if !ok { continue }
        if f.bfs_prev[ns] == -1 {        // first discovery wins → insertion-order determinism
            f.bfs_prev[ns] = i32(cur)
            f.bfs_queue[tail] = ns; tail += 1
        }
    }
}

What you're seeing · determinism notes
  • One path per packet, computed at spawn and cached on Packet.route. The packet never re-decides mid-flight unless its current pipe is demolished (E1 severance).
  • Parallel pipes between a node pair: a basic junction round-robins (rr_next, even split, ignores capacity); a smart junction picks the highest-capacity pipe with round-robin only among ties (pick_pipe).
  • QoS lanes are bandwidth-on-a-pipe, not routing: capacity splits Express→Standard→Best by WFQ, work-conserving, with a floor so a lone class isn't starved.
  • Drops: Queue_Overflow (per-lane depth 60), Pool_Exhaustion (6000), Unreachable (E28 — accrues, never spawns), Severance (E1).
  • The sim draws from a seeded JS RNG only for spawn-time weighted_pick — routing itself is deterministic by insertion order. ms_per_tick = 100 (logic_hz 10).

Round-robin vs. capacity-weighted across parallel pipes

A smart junction (mid/high router) sends everything down the fattest pipe. Send a burst and watch the tally diverge.

🍍 your idea · a 4th alternativesimplification play

Merge parallel pipes into one pooled-capacity link

Treat all pipes between a node pair as one logical link whose capacity is the sum of its members — no round-robin, no capacity-weighted LB, no ECMP. Routing just sees one fat edge. You hit the real driver: under today's model a 2nd link is insurance (idle until severance), so it feels like wasted ports — merging makes redundancy active capacity the moment you build it.

What it gains
  • Redundancy is useful immediately — a 2nd link adds capacity now, used in spikes (not idle insurance).
  • Deletes an entire mechanic (basic vs smart LB, RR vs weighted) → less cognitive load.
  • Deletes gap #3 outright — nothing left to disagree about.
  • Trivially deterministic; keeps the Mini Motorways clarity the GDD wants.
What it costs — the “more fun?” crux
  • Erases the “basic RR wastes the fiber” teaching moment (§M3 / FORGE #1) + the smart-router upgrade path (M4).
  • Removes a player skill lever (the LB-mode choice).
  • Merging ≈ optimal LB, so it deletes the failure mode (copper saturating while fiber idles) that creates puzzle tension.
  • Softens the Severance crisis (M5): losing one pipe of a bundle just drops capacity (60→40), not a hard cut.
Strategic angle: the game's real differentiator is packet-types + QoS (FORGE #4), not LB — so merging LB away concentrates cognitive budget on QoS (where it's unique) and helps the engineer/non-engineer bridge. That's a real point in favor. Middle path: a “bundle” (LAG/LACP metaphor) that routes as one pooled link by default, with LB-mode as an optional per-bundle depth dial. Your call — annotate, or pick it in Decide.

④ Proposed · not in the prototype

Equal-Cost Multi-Path: split across disjoint paths

Today, BFS commits a packet to the one insertion-first shortest path. ECMP instead recognizes all equal-hop routes to the sink and spreads packets across them — real routers do this. Toggle it on and send a burst through the two equal-cost paths below. Watch load spread — and note the reordering side effect (out-of-order arrival), which matters for streaming/voice.

Determinism hook (ODN-9/10): ECMP needs a seeded choice per packet — a hash of (src,dst,class,id) mod N, or the owned RNG. Either keeps replay byte-identical; an unseeded split would shatter the determinism spine. This is the #1 thing to get right if you build it.
⑤ Proposed · not in the prototype

What if routers decided the next hop, per packet?

Instead of committing to a full path at spawn, each junction runs a forwarding lookup on (src, dst) and picks the next hop — re-deciding live, at every node, against whatever the topology looks like right now. Toggle between the two models and watch the same demolition play out differently.

⑥ Proposed · a reasoned survey, not a build

“Implement a simple IS-IS / BGP?” — should you?

A lite link-state (IS-IS/OSPF-style: every node floods its neighbors, everyone solves shortest-path) or path-vector (BGP-style: advertise reachable destinations with policy) control plane is the "real networks do this" answer. Here's the honest cost/benefit, grounded in what's fun and legible for this game (GDD pillars P1 routing-satisfaction, P2 packet-type trade-offs).

What it buys

  • Real route computation — cost-weighted, policy-aware (e.g. "prefer fiber", "avoid this ISP").
  • Automatic convergence: the network re-solves itself after edits, no manual re-BFS.
  • A new depth vein: policy as a player lever (QoS-adjacent, but at the topology level).
  • Educational byproduct (FORGE #1) goes up — players learn how the internet actually routes.

What it costs

  • Complexity: flooding + LSDB + SPF (or path attributes + selection) is a whole subsystem vs. one ~40-line BFS.
  • Sim-tick expense: periodic recompute + convergence churn (see ⑦ for the numbers).
  • Determinism threat: convergence is asynchronous by nature — you'd have to serialize it onto the tick to keep ODN-10, which fights the metaphor.
  • Legibility: "why did my packet go that way?" gets harder to show — bad for P1's readable panic.
my read

Recommendation

Don't build it for launch. The prototype's BFS+LB+failover already delivers P1 (the routing-satisfaction loop) and P2 (QoS trade-offs) at a fraction of the cost. Reserve a control plane for Era 6 (Software-Defined Edge) — the GDD already abstracts that era deliberately, and "programmable reroute / policy routing" lands there naturally as a mechanic, not as hidden plumbing. If you want more routing depth now, ECMP + per-hop forwarding (④⑤) get you 80% of the feel for ~20% of the complexity.

This is a your-call framing — annotate if you disagree.

The forge guardrail (FORGE #2): the core mechanic is draw + react, not configure a router OS. A control plane is only justified if it makes the player's drawing decisions richer — not if it turns Packet Plumber into a Cisco sim.

🍍 Your perf idea — a packet scale-factor: you don't have to simulate 6000 discrete packets. A scale factor (1 sim packet = N real packets) is a legit, classic sim optimization: coarse-grain traffic into “macro-packets” and per-tick work drops by ~N× (fewer entities to route + serve). It stays deterministic as long as the aggregation rule is fixed (demand always rounds the same way). The trade is resolution: coarser packets mean a coarser SLA/latency signal and choppier drops — fine at full-game scale where you want throughput, less fine in the PROTO where you're tuning the feel of a single drop. Recommendation: keep 1:1 for the PROTO fun-gate (you want to see every packet), introduce the scale-factor as a full-game performance tier once the feel is locked. The 6000 here is just balance.json:packet_pool_cap — a ceiling, never a target. (Origin, since you asked:) not my number — it's the catalog value ported from the Godot prototype's tuned set; at PROTO scale the per-lane queue depth (60) sheds long before 6000 in-flight packets ever accumulate, so it's a pure safety backstop (E22), not a binding constraint. A skillful player growing the topology at full-game scale is exactly when you'd revisit it — raise the cap, lean on the scale-factor, or both. It's a one-line catalog knob; replay tests catch any behavior change.

Where the real CPU goes today

advance iterates every live pipe and, within each, walks the packet list to serve by lane — that's the hot loop, not BFS. BFS runs only at spawn and is already negligible at PROTO scale. So routing-strategy cost is mostly about how often you re-decide, not the algorithm's constant factor.

Full-game scale (64→hundreds of nodes)

BFS-per-spawn stays fine (O(V+E), cache amortizes). Per-hop forwarding scales linearly with packets×hops — still cheap. The control plane is the one that can bite: SPF on a few hundred nodes is fine, but convergence churn under rapid player edits could spike. The determinism constraint, not throughput, is the binding one.

🔒 Determinism design · ODN-9/10 spine · your direct ask

Per-hop forwarding + ECMP, kept byte-replay-identical

You asked how per-hop forwarding + ECMP avoid the determinism risk. Done right, it's as deterministic as today's BFS — replays stay bit-identical. The whole rule: every hop decision is a pure function of (topology, packet identity) — no wall-clock, no map iteration, no float, no async.

① Forwarding table, rebuilt on topology change only

Each junction holds a lookup (junction, dst) → next hop, computed by a deterministic BFS/SPF with insertion-order tie-breaks (the same rule compute_route uses today). Rebuild it only when a Command changes the topology, synchronously inside flow_step — never asynchronously. That single move kills the “async convergence” threat that made a live IS-IS/BGP plane risky.

② ECMP choice = a seeded hash of the packet

Among N equal-cost next hops, pick hash(src, dst, class, packet_id) mod N. The hash is a fixed integer finalizer — reuse the project's splitmix64 from ODN-9 — so same packet → same choice on every replay, with zero dependence on sim RNG or processing order. Bonus: flow affinity (all packets of one flow take one path → no intra-flow reordering). This is real-router 5-tuple ECMP, and it's perfectly reproducible.

Why the path is still reproducible: a packet's full route becomes a pure function of (topology, packet identity, hash fn). It's decided hop-by-hop at runtime, but the result is identical every replay — so you may still cache it after first compute (recompute on topology change) for speed. Determinism doesn't care whether you cache; it only cares that the function is pure.
The 4-rule ODN-9/10 checklist:
  1. Forwarding table rebuilt only on topology change, inside the tick (synchronous — no async convergence).
  2. ECMP tie-break = pure hash of packet identity, integer-only, pinned finalizer (no sim-RNG draw).
  3. No map iteration in the hot path — tables are arrays indexed by slot, insertion-ordered.
  4. Pin it with a replay test (ODN-17): same seed + same commands → byte-identical snapshot, per-packet paths included.
Satisfy those four and per-hop + ECMP is as deterministic as BFS-by-insertion-order. The spine holds.

And none of this is player-facing (your call): players draw pipes; the engine routes. The forwarding table is an implementation detail, not a UI surface — no config CLI, no “router OS”.

⑧ Current + proposed · the Surge scenario (demand.json)

Failover during a spike

The Surge is streaming ×10 for ~1800 ticks with a 600-tick forecast (Era 3 climax). Ramp demand into a topology with a redundant link and watch how each model copes. Today, redundancy is insurance — it only kicks in on severance/saturation. Under ECMP or per-hop forwarding, redundancy is active from the first packet. The no-soft-lock rule (always a way to reroute) must hold in all three.

Read it like the player would: under current, the primary path saturates and drops climb until severance/overflow reroutes onto the backup — there's a visible droop. Under ECMP / per-hop, both paths share load from tick 0, so the droop is shallower — but you've spent the redundancy early, leaving less cushion for a second failure. That trade-off is the whole game.

Where the docs and the prototype disagree

The briefing asked me to surface these — they're not bugs, they're forks the design docs describe one way and the merged prototype implements another. Each one is a place where "what to build for the full game" is an open question.

🍍 Context you flagged: the current code is the prototype playability gate, not the final model — the full-game epics/stories aren't written yet and the architecture will likely update to match whatever routing direction lands. So read these gaps as a full-game TODO list, not prototype defects. Concretely: ▲1 (tier-cost routing) and ▲4 (clean-span degradation) are consciously deferred to the full game; ▲2 (route migration) you've just resolved by going per-hop (forwarding re-decides live, so “migration” is automatic); ▲3 (proportional vs greedy LB) is moot once parallel pipes bundle (no LB to disagree about).
gap 1

Routing metric: tier-cost vs. hop-count

Arch §6.2 (L901) specifies "deterministic shortest-path-by-tier-cost with seeded tie-break." The code (compute_route) is plain BFS by hop count — edges are unweighted, neighbors break ties by insertion order, and no RNG is drawn in routing.

Implication: today a 3-hop all-fiber route loses to a 2-hop all-copper route. Tier-cost routing would change which paths win and is a real design choice.

gap 2

Route migration: node-boundaries vs. severance-only

Arch E29 describes in-flight packets re-routing at every node boundary (reactive to topology/load). The code re-runs compute_route only on severance (E1) — otherwise a packet's route is frozen at spawn for its entire life.

Implication: the "load-aware, self-healing" feel E29 implies isn't live. Per-hop forwarding (⑤) is essentially implementing E29 as designed.

gap 3

Smart LB: proportional vs. greedy-max

GDD §M3 says smart junctions split "proportional to pipe tier." The code (pick_pipe) is greedy-highest-capacity: it always picks the fattest pipe, round-robining only among ties at the max. A fiber+standard bundle sends nothing down the standard pipe.

Implication: "weighted LB" today is really "best-pipe LB." Proportional splitting would actually utilize mixed bundles — closer to the GDD intent.

bonus

Span / clean-span — enforced max only

M1 describes a soft clean span (throughput degrades beyond it) plus a hard max span. The prototype enforces only the hard max at draw/upgrade (validate_command); pipe_capacity is a flat tier constant, no degradation curve.

Not routing per se, but it interacts: span-cost routing (gap 1) and clean-span degradation would reinforce each other as full-game depth.
