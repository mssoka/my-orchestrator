M-1 · Medium ✅ parent-verified

Stripe unlock webhook never checks payment_status

payment/webhook_handler.gleam:313-380 — verified absent across the file

Exploit sketch
payment_method_types is not restricted at session creation. If the Stripe Dashboard ever allows async methods (SEPA, Boleto, Klarna), checkout.session.completed fires with payment_status: processing/unpaid — the handler unlocks the vacancy and fires burst AI scoring immediately; funds can still fail days later. No refund/dispute handling compounds it (L-7).
Remediation
Gate the unlock on payment_status == "paid" (anything else: ack and wait), or restrict payment_method_types: ["card"] at session creation so completed ⇒ paid.
M-2 · Medium ✅ parent-verified

Documented edge rate limits do not exist

deployment/cloudflare-worker/worker.js:588 ("Deliberately omitted") · terraform/cloudflare-rate-limits.tf (Free tier = 1 rule, spent on /erase/+/dsar/)

Exploit sketch
AGENTS.md documents login 10/min, signup 5/h, apply-submit 5/h per IP — none implemented. Nuance: GoTrue throttles login/signup (the code maps its 429s), and resend-confirmation has a Worker limit + DB cooldown. Practical gap: POST /apply/:code (22MB multipart, storage writes, email sends, AI-queue inserts — unbounded per IP) and /auth/recover spam.
Remediation
Extend the Worker's per-IP AUTH_WRITE_PATTERN bucket to /apply/* POSTs (Worker counters bypass the 1-rule cap by design); correct AGENTS.md; add account-aware auth limits when a paid plan frees the ruleset slot.
M-3 · Medium ✅ parent-verified (citation corrected)

CI deploy identity is a full-project takeover primitive

deployment/terraform/iam.tf:86-103 — projectIamAdmin + serviceAccountAdmin + workloadIdentityPoolAdmin

Exploit sketch
Anyone who can push to main/staging (or compromise a runner) authenticates as the deploy SA via WIF and runs terraform apply — which can grant itself any project role, mint SAs, re-point WIF. One compromised merge ⇒ full GCP project control, including every secret in Secret Manager.
Remediation
Split the Terraform-apply identity from IAM administration: narrow the CI SA (artifactregistry.writer, run.developer, per-secret secretVersionAdder), move IAM/SA/WIF changes to a separately-triggered, human-gated workflow. Minimum: required reviewers on the production environment + document the SA as effectively project-owner.
M-4 · Medium ✅ parent-verified

PostHog autocapture scrapes dashboard PII, no text masking

Makefile:193 / Dockerfile:62 — no mask_all_text, autocapture defaults on, person_profiles: identified_only

Exploit sketch
For a landlord who accepts analytics cookies, autocapture records clicks + input text across the dashboard — applicant names, emails, addresses, scores render in the DOM and are captured as identified events to the EU cloud. Consent to analytics doesn't clearly cover applicant PII to a third party — a GDPR transparency risk more than an exploit. Server-side identify also ships the landlord email as a $set property, consent-independent (I-2).
Remediation
Set autocapture: { mask_all_text: true } (or disable autocapture — pageviews + named events already cover product analytics); document the capture scope in the privacy policy.
M-5 · Medium ✅ parent-verified

x-forwarded-for first-value trust feeds consent records + Meta CAPI

request_helpers.gleam:40-53 → cookie_consent_log.ip_text · submitted_ip_text · CAPI client_ip

Exploit sketch
Safe behind Cloudflare (CF overwrites the header). Direct-to-origin requests can spoof it: forged evidentiary IPs in consent/audit records and an attacker-chosen IP injected into Meta CAPI payloads. Bounded by the X-RT-Secret origin lock — which itself has the L-19/L-20 weaknesses.
Remediation
Prefer cf-connecting-ip (unforgeable at the edge, present on all proxied requests); fall back to empty when absent rather than trusting client-supplied XFF.

PII reaches logs on error paths (3 findings, one verdict)

  • M-6 · ai/ai_client.gleam:1044,1170,1189,1340 — raw ADK bodies on parse failure (applicant data)
  • M-7 · auth/supabase.gleam:308,632,651 — raw Supabase error bodies (echo email)
  • M-8 · reference_checks/lookup.gleam:85-93 — raw phone number to Cloud Logging + Sentry
Exploit sketch
Intermittent (failure-path only), but when they fire, applicant PII lands in Cloud Logging and Sentry. The codebase otherwise has disciplined redaction (token-route redaction, CrashEvent header allowlist, masked emails) — these four paths bypass it.
Remediation
Route bodies through a scrubbing helper (truncate + strip emails/phones/tokens) or log status + event id only — the one-line pattern the codebase already uses elsewhere. Also L-13 (digest logs email) rides the same fix.

Verified clean (the good news)

Data layer
SQL injection architecturally impossible — all 227 queries Squirrel-parameterized; the single raw query is a static SET LOCAL. All six Erlang FFIs clean (no binary_to_atom, no shell wrapping, UUID-minted temp paths). Sentry CrashEvent headers pass a six-header allowlist.
AuthN (strongest layer)
OAuth/PKCE: provider allowlisted, fixed redirects, verifier-cookie = state binding. Cookies: Signed HMAC-SHA512, HttpOnly, SameSite=Lax, __Host- in prod. Password reset: one-shot atomic nonce. Meta CAPI consent-gated and fire-once. No Medium+ findings.
SSR/render
Every sink walked: Lustre/houdini full escaping on text + attributes; raw-JS sinks carry server-generated URL-safe values only; content pages are compile-time constants; static traversal unexploitable (stdlib splits raw + RFC dot-segment removal). No Medium+ findings.
Webhook signatures
Stripe, Svix (Resend), and Twilio all HMAC-verified with crypto.secure_compare; 5-min tolerance windows; event-id dedup + idempotent state transitions; uploads magic-byte-validated with UUID paths; document downloads ownership-checked with 15-min signed URLs. No SSRF sink found.
