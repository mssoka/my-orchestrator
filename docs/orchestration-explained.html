How the orchestrator works

One pi “Gru” session at ~/code dispatches work to ephemeral minions. Everything below reflects the live system as of 2026-07-20.

The 30-second version

You give Gru a job. It writes a briefing, asks Herdr for a git worktree + terminal pane, launches a fresh pi agent there, and hands over. The minion does the work using BMAD skills (usually bmad-quick-dev), self-reports every status change into a SQLite ledger via bin/ledger, and opens a PR. A pi extension, nefario-watch, polls Herdr every 30s and wakes Gru whenever a minion stops — so clarify questions get relayed to you instead of sitting unnoticed. You review and merge the PR. Gru never implements and never merges.

The cast

pi Gru session

The orchestrator. A pi agent whose cwd is /Users/moses/code. Dispatches, relays, tracks. Never writes code in a main checkout, never merges PRs.

.pi/extensions/gru.ts

Project-local pi extension (loads only in the root). Injects standing orders into the system prompt every turn (survives compaction), fires the startup checklist, re-grounds after compaction.

.pi/extensions/nefario-watch.ts

The watcher. Polls herdr agent list every 30s, diffs ledger-tracked panes, and injects a message into Gru session when one stops or vanishes. See § nefario-watch.

Herdr

Terminal multiplexer + agent runtime. Workspaces → tabs → panes. Detects agent identity/status (idle · working · blocked · done), creates git worktrees, delivers notifications, long-poll waits.

BMAD skills

bmad-* skills installed per repo by the BMAD installer, symlinked into ~/.pi/agent/skills/ so they resolve from any worktree. Minions execute with bmad-quick-dev; personas like Paige (tech writer) produce copy decks.

SQLite ledger

_bmad-output/orchestrator.db — durable state across Herdr restarts. Two tables: jobs (current state) + job_events (audit trail). Replaced the old YAML file on 2026-07-20.

bin/ledger

python3-stdlib CLI over the DB. Used by Gru, by minions (self-reporting), and by nefario-watch (read-only). WAL mode + busy timeout → safe for concurrent writers.

Minions

Ephemeral pi agents in Herdr panes, one per job, each in its own worktree on its own branch. May spawn their own mega-minions (must close them). Fire herdr notification show when blocked/finished.

gh / GitHub

Minions push their branch and open PRs against the repo’s base branch (develop for RightTenantry). The human reviews and merges.

Job lifecycle — step through it

The ledger: what the SQL looks like

Two tables. jobs is current state (one row per job); job_events is the append-only audit trail — every transition, every note, timestamped.

Schema (DDL) 
CREATE TABLE jobs (
  id TEXT PRIMARY KEY,
  repo TEXT, repo_root TEXT, slug TEXT, base TEXT,
  model TEXT, worktree TEXT, pane_id TEXT, tab_id TEXT,
  status TEXT NOT NULL DEFAULT 'dispatched'
    CHECK (status IN ('dispatched','clarifying','working',
                      'in-review','blocked','done')),
  started_at TEXT, briefing TEXT, pr TEXT, result TEXT,
  github_issue INTEGER, parent TEXT, note TEXT
);

CREATE TABLE job_events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  job_id TEXT NOT NULL REFERENCES jobs(id),
  ts TEXT NOT NULL,
  from_status TEXT, to_status TEXT, note TEXT
);

How minions update the database

Every briefing carries this standing order:

/Users/moses/code/bin/ledger set <job-id> <status> "<one-line note>"

The minion runs it at each transition — clarifying when it halts with questions, working when answers arrive, in-review when the PR opens. bin/ledger updates the job row and appends a job_events row in one transaction. WAL mode + a 5s busy timeout make concurrent writers (4+ agents at once) safe.

This already works in production: after Gru relayed the clarify answers for issue #530, the minion logged clarifying → working — "clarify answered; planning per copy deck 2026-07-20" within seconds — unprompted beyond the standing order.

Why not YAML? Concurrent edits of one YAML file corrupt; SQLite gives atomic writes, targeted reads (WHERE status != 'done'), and an audit trail the YAML never had.

How Gru finds out: nefario-watch

The gap it fixes: a pi agent halted at its prompt reports idle — indistinguishable from “finished and seen”. Minions toast the human with herdr notification show, but that toast is fire-and-forget: Gru cannot read it, and pi only runs when invoked.

every 30s→ herdr agent list→ SELECT … FROM jobs WHERE status != 'done'→ diff per tracked pane→ pi.sendMessage(triggerTurn: true)→ Gru wakes, reads transcript, classifies, relays
Herdr statusMeaningWatcher behaviour
workingAgent is mid-taskNo alert (re-arms the alert for the next stop)
idleAt prompt; result “seen” — could be a clarify haltAlert once on transition into it
doneFinished while unseen (background tab)Alert once on transition into it
blockedNeeds inputAlert once on transition into it
pane goneHerdr restart / manual closeAlert once; Gru re-resolves ids

Alert delivery is deliverAs: "followUp" — it never interrupts Gru mid-turn; it lands when the current turn finishes. At session start it takes a silent snapshot and posts a catch-up digest (nextTurn) for anything that stopped while Gru was down. Only ledger-tracked panes are watched, and alerts fire on transitions, so a halted agent doesn’t re-alert every 30s.

The human loop

1. Toast

Minion fires herdr notification show "<job>" --body "…" on blocked/finished → your terminal notifications, even if nobody is watching.

2. Wake

nefario-watch notices the stopped pane and wakes the Gru, which reads the transcript and classifies: clarify halt? finished? error?

3. Relay

Clarify questions are pasted to you verbatim; your answer goes back via herdr pane run <pane> "…". Ledger updated at each hop.

4. Review

PR opens targeting the base branch; job → in-review. You review and merge. Gru never merges. After your ack: panes closed, worktree + branch removed, job → done.
